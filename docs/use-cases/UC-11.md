# UC-11 · Aprobar y registrar customer nuevo + application

| Campo | Valor |
|---|---|
| **Fase** | 3 — Aprobación y persistencia transaccional |
| **Tipo** | Negocio |
| **Actor** | Sistema NiuroTest |

## Actores y proyectos involucrados

- `backend/` (`Niuro.Api`): recibe el request aprobado y delega el caso de uso.
- `core/` (`Niuro.Core`): caso de uso `SubmitLoanApplication` (application layer) + `NiuroDbContext` (infraestructura) + entidades.
- BD PostgreSQL: tablas `Customers`, `Applications`, `OutboxEvents`.

## Descripción

La solicitud fue aprobada (UC-08) y el SSN **no existe** en la BD → se crean `Customer`, `Application` y el evento de outbox **en una sola transacción**. Todo se commitea junto o nada.

## Contrato técnico (backend → frontend)

```
200 OK
{ "status": "approved", "applicationId": "<guid>", "reason": null }
```

La respuesta se devuelve **después** del commit de la transacción, **sin** esperar al envío en background (UC-13).

## Flujo principal (caso de uso `SubmitLoanApplication`)

1. Normalizar el SSN al formato con guiones `###-##-####` y buscar el Customer por ese SSN para confirmar que **no existe** (si existiera → UC-12).
2. Crear `Customer` con los datos del formulario (SSN ya normalizado).
3. Crear `Application` (`Id`, `CustomerId`, `RequestedAmount`).
4. Crear el evento de **outbox** (`OutboxEvent`) con:
   - `Operation = Create`
   - `Payload` = customer + application (JSON) — el mismo shape que enviará el worker al mock (UC-13/14).
   - `Status = Pending`
5. `SaveChanges()` → **una sola transacción** implícita del `DbContext` (unit of work): `Customer` + `Application` + `OutboxEvent` se commitean juntos.

## Transacción — qué pasa si falla

- `SaveChanges()` usa la transacción implícita de EF Core/PostgreSQL: si **cualquier** escritura falla (DB caída, constraint, error de conexión), **todo hace rollback**: sin customer a medias, sin application huérfana, **sin evento en `OutboxEvents`** → nada se publica nunca. Esto satisface "no event published".
- El `IExceptionHandler` del API loguea el error (Serilog, `Service=Niuro.Api`) y devuelve `500` con Problem Details. El frontend muestra error con reintento.

## Implementación técnica

- `core/Infrastructure`: `NiuroDbContext` (DbSet `Customers`, `Applications`, `OutboxEvents`) con migraciones reales PostgreSQL (UC-06). No se usa el provider in-memory.
- `core/Application`: `SubmitLoanApplication` — método `async` con `CancellationToken`; recibe el DTO ya validado; orquesta: normalizar SSN → buscar customer → ramificar create/update → evaluar no es necesario aquí (ya se evaluó en UC-08) → `SaveChangesAsync`.
- **EF idiomático**: `DbContext` es ya unit of work y repository para CRUD trivial; sin capas de repositorio propias salvo que un agregado lo justifique.

## Postcondiciones

- Quedan persistidos Customer + Application + evento outbox, atómicamente.
- Se responde al frontend la aprobación (`applicationId`).
- El evento `Pending` lo procesará el worker (UC-13).
