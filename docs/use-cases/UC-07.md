# UC-07 · Enviar solicitud de préstamo

| Campo | Valor |
|---|---|
| **Fase** | 1 — Solicitud y decisión |
| **Tipo** | Negocio |
| **Actor** | Solicitante · Sistema NiuroTest |

## Actores y proyectos involucrados

- **Solicitante** → `frontend/` (formulario Next.js, cliente).
- `frontend/` → `backend/` (`Niuro.Api`): `POST /api/loan-applications`.
- `backend/` → (interno) rule engine de `core/` (UC-08).

## Descripción

El solicitante ingresa los 6 campos (first name, last name, address con **state**, company name, requested amount, SSN) y envía el formulario. El frontend hace `POST` al backend, que valida la entrada, corre el rule engine (UC-08) y responde la decisión.

El address se modela como objeto estructurado: `street`, `city`, `state`, `zipCode`.

## Contrato técnico (frontend → backend)

```
POST http://localhost:5100/api/loan-applications
Content-Type: application/json
```

**Request body:**
```json
{
  "firstName": "John",
  "lastName": "Doe",
  "address": { "street": "123 Main St", "city": "Buffalo", "state": "NY", "zipCode": "14201" },
  "companyName": "ACME Inc",
  "requestedAmount": 25000.00,
  "ssn": "123-45-6789"
}
```

**Respuesta `200 OK`** (Result Pattern: aprobado y denegado son `200`; el tipo vive en el payload):
```json
// Aprobado
{ "status": "approved", "applicationId": "0198-...", "reason": null }
// Denegado
{ "status": "denied", "reason": "STATE_NY", "applicationId": null }
```

**Otros códigos:**
- `400`/`422` con **Problem Details** (RFC 9457): payload inválido (campos vacíos, monto ≤ 0, SSN malformado, address incompleto). El body incluye el detalle por campo.
- `500` con **Problem Details**: error inesperado (solo lanzados por el `IExceptionHandler`), nunca por flujo esperado.

## Precondiciones

- Backend y frontend corriendo.
- `NEXT_PUBLIC_API_URL=http://localhost:5100` disponible vía `useConfig()` (UC-05).

## Flujo principal

1. El solicitante llena el formulario en `frontend/` (componente cliente con controles PrimeReact).
2. El frontend valida en cliente (mensajes inline y accesibles).
3. El frontend hace `fetch` a `POST /api/loan-applications` con el payload JSON.
4. El backend valida el payload **antes** del rule engine; si es inválido responde `400`/`422` con Problem Details por campo.
5. El backend corre el rule engine (UC-08) y devuelve el `Result`.
6. `200` con `status`:
   - `approved` → el frontend navega a la página de **éxito** (muestra el `applicationId`).
   - `denied` → el frontend navega a la página de **denied** mostrando el motivo legible del `reason`.

## Excepciones

- **Payload inválido** (400/422) → el frontend muestra los errores por campo del Problem Details bajo cada input.
- **Error de red / backend caído** → el frontend muestra un error claro con opción de reintentar (sin romper el estado del formulario).
- **Respuesta inesperada** (no 2xx ni forma esperada) → manejo genérico de error.
- El frontend **no** decide aprobación/denegación: solo muestra lo que trae el `status` del API.

## Implementación técnica

- **`core/`**: `LoanApplicationRequest` (DTO de entrada), `Result`/`Result<T>` (Success/Failure), `LoanDecision` (status + reason).
- **`backend/`**: controller delgado (`LoanApplicationsController`) que recibe el DTO, llama al caso de uso de `core/` y traduce el `Result` a `200`/400/422/500. Validación con DataAnnotations / validación built-in normalizada a Problem Details. Configura `AddProblemDetails()` + `IExceptionHandler` para los `500`.
- **`frontend/`**: página `/` con `LoanApplicationForm` (client component), hook `useConfig()` para la URL, estados `idle | loading | success | denied | error`.

## Postcondiciones

- La solicitud queda evaluada: aprobada (continúa a UC-11/12) o denegada con motivo visible (UC-09/10), ambas en `200` con el tipo en el payload.
- El solicitante vio su resultado; en caso de aprobación, nada de esto espera al proceso en background (UC-13).
