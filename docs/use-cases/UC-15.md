# UC-15 · Consultar registros recibidos por el mock

| Campo | Valor |
|---|---|
| **Fase** | 4 — Evento en background al servicio externo |
| **Tipo** | Desarrollo (demo/verificación) |
| **Actor** | Equipo de desarrollo |

## Actores y proyectos involucrados

- `mock/` (`Niuro.Mock`): expone el endpoint de solo lectura sobre su estado en memoria.
- Equipo de desarrollo (o navegador/curl): consume el endpoint para verificar la demo.

## Descripción

Endpoint de solo lectura del mock que lista lo recibido (UC-14), para poder validar en la demo que el evento llegó con los datos correctos: aprobado → llega create; denegado → **nunca** llega; customer que regresa → **actualizó** (no duplicó) en el servicio externo.

## Contrato técnico

```
GET http://localhost:5200/api/customers

200 OK
[
  {
    "ssn": "123-45-6789",
    "lastOperation": "create" | "update",
    "lastUpdatedAt": "2026-08-12T10:00:00Z",
    "customer": { "firstName": "John", "lastName": "Doe", "address": { "street": "123 Main St", "city": "Buffalo", "state": "NY", "zipCode": "14201" }, "companyName": "ACME Inc", "ssn": "123-45-6789" },
    "application": { "id": "0198-...", "requestedAmount": 25000.00 }
  }
]
```

- Lista **keyed por SSN** (un elemento por SSN: crear + actualizar = el mismo elemento con `lastOperation: "update"` y datos actualizados).
- Orden: por fecha de última operación o inserción (a criterio; documentar el elegido).

## Flujo principal

1. El equipo consulta `GET /api/customers` en el mock (`http://localhost:5200`).
2. El mock devuelve el array de registros recibidos con su `lastOperation` (create/update).
3. El equipo valida contra lo esperado de la demo:
   - Solicitud aprobada nueva → entrada con `lastOperation: create`.
   - Solicitud aprobada repetida (mismo SSN) → **1 sola** entrada, `lastOperation: update`, datos más recientes.
   - Solicitud denegada (NY o blacklist) → **no aparece**.
