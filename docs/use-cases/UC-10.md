# UC-10 · Denegar por SSN en blacklist

| Campo | Valor |
|---|---|
| **Fase** | 2 — Denegación |
| **Tipo** | Negocio |
| **Actor** | Sistema NiuroTest · Solicitante |

## Actores y proyectos involucrados

- `core/` (`Niuro.Core`): la regla `BlacklistedSsnRule` del engine (UC-08), que consulta `BlacklistedSsn` vía `IBlacklistedSsnQuery`.
- BD PostgreSQL: tabla `BlacklistedSsn` seedada por la migración del UC-06.
- `backend/` (`Niuro.Api`): traduce el `Result` a HTTP.
- `frontend/`: página de denied con el motivo.

## Descripción

Si el SSN está en la **blacklist** (seedeada por migración, UC-06) → la solicitud es denegada. Se muestra la página de denied con el motivo.

## Contrato técnico (backend → frontend)

Dentro del `POST /api/loan-applications` del UC-07:

```
200 OK
{ "status": "denied", "reason": "SSN_BLACKLISTED", "applicationId": null }
```

**NO es un error HTTP** (Result Pattern). El SSN se normaliza a guiones antes de comparar.

## Precondiciones

- El payload pasó la validación de entrada (UC-07).
- La tabla `BlacklistedSsn` está seedeada (UC-06).

## Flujo principal

1. Normalizar el SSN al formato con guiones `###-##-####` (el campo es string; se aprovecha para estandarizar, como en UC-11/12).
2. `RuleEngine.EvaluateAsync` aplica `BlacklistedSsnRule`: consulta `IBlacklistedSsnQuery.IsBlacklistedAsync(ssn)`.
3. Si el SSN está en la blacklist → aplica → el engine devuelve `Result` `Failure` con `ReasonCode = "SSN_BLACKLISTED"`.
4. El controller responde `200` con `{ status: "denied", reason: "SSN_BLACKLISTED" }`.
5. El frontend muestra la página de denied con el mensaje legible ("El SSN está en la lista de denegados").

## Excepciones

- Formato de SSN inconsistente (guiones vs. sin guiones) → se resuelve normalizando siempre a guiones before de comparar.

## Postcondiciones

- La solicitud queda denegada. **No se persiste nada** y **no se publica ningún evento**.
