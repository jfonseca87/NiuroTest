# UC-08 · Evaluar la solicitud con el rule engine

| Campo | Valor |
|---|---|
| **Fase** | 1 — Solicitud y decisión |
| **Tipo** | Negocio |
| **Actor** | Sistema NiuroTest |

## Actores y proyectos involucrados

- `backend/` (`Niuro.Api`) delega la decisión al motor de reglas.
- `core/` (`Niuro.Core`) contiene el rule engine (dominio/application).
- La regla de blacklist consulta la tabla `BlacklistedSsn` de la BD (seed del UC-06).

## Descripción

El motor de reglas evalúa la solicitud y decide `Approved` o `Denied` con su motivo. La lógica vive centralizada en un engine dentro de `core/` (dominio/application), nunca en el controller ni en el frontend. Agregar una regla nueva NO requiere modificar las existentes (Open/Closed).

## Precondiciones

- La solicitud pasó la validación de entrada (los datos son válidos).

## Diseño técnico del rule engine

Interfaz de regla (una por regla, en `core/Domain/Rules`):

```csharp
public interface IDenialRule
{
    string ReasonCode { get; }          // p. ej. "STATE_NY"
    Task<bool> AppliesAsync(LoanCandidate candidate, CancellationToken ct);
}
```

- `LoanCandidate`: value object simple que agrupa los datos que las reglas evalúan (`State` normalizado a mayúsculas, `Ssn` normalizado a guiones y opcionalmente `requestedAmount`).
- **`RuleEngine`**: recibe `IEnumerable<IDenialRule>` (registradas por DI); evalúa en orden; la **primera** que aplique decide `Denied` con su `ReasonCode`; si ninguna aplica → `Approved`. Agregar una regla = crear la clase + registrarla en DI (registrar en el `Program` del API o al registrar la librería de dominio). No se modifica el engine ni las otras reglas.

**Reglas de la Fase 2:**
| Regla | Razón (código) | Condición |
|---|---|---|
| `StateNyRule` | `STATE_NY` | `state` (mayúsculas) == `"NY"` |
| `BlacklistedSsnRule` | `SSN_BLACKLISTED` | `ssn` (guiones) existe en `BlacklistedSsn` |

`BlacklistedSsnRule` depende de `IBlacklistedSsnQuery` (interfaz), implementada en infraestructura con EF Core (`core/Infrastructure`). Esto mantiene el dominio sin dependencia de infraestructura.

## Flujo principal

1. El engine recibe el `LoanCandidate` (state normalizado a mayúsculas, SSN normalizado a guiones).
2. El engine aplica cada `IDenialRule` registrada (evalúa `AppliesAsync`).
3. Si alguna aplica → `Result` `Failure` con motivo (`ReasonCode`).
4. Si ninguna aplica → `Result` `Success` con decisión `Approved`.

**Result Pattern en el API**: el controller traduce el `Result` a HTTP: `approved` y `denied` responden **`200 OK`** y el tipo queda en el payload (`status` + motivo si aplica). 4xx NO se usan para denegación; solo payload inválido (400/422) y 500 inesperado.

## Excepciones

- El engine no lanza errores por flujo esperado; devuelve `Result` (`Success`/`Failure`).
- El engine **no consulta la BD** de customer/application: esa decisión pertenece a la Fase 3. Solo evalúa reglas de denegación.

## Postcondiciones

- Decisión con motivo (si aplica). La decisión NO persiste nada por sí misma.

## Tests a cubrir (criterio de evaluación)

- Unitarios del rule engine: `STATE_NY`, `SSN_BLACKLISTED`, aprobación sin reglas que apliquen.
- Agregar una regla nueva (regla fake extra) sin modificar las existentes → Open/Closed demostrado.
- La blacklist se prueba con un `IBlacklistedSsnQuery` fake (los tests no requieren DB).
