# UC-12 · Actualizar customer que regresa + application

| Campo | Valor |
|---|---|
| **Fase** | 3 — Aprobación y persistencia transaccional |
| **Tipo** | Negocio |
| **Actor** | Sistema NiuroTest |

## Actores y proyectos involucrados

- `backend/` (`Niuro.Api`): recibe el request aprobado y delega el caso de uso.
- `core/` (`Niuro.Core`): mismo caso de uso `SubmitLoanApplication` del UC-11 (rama "regresa") + `NiuroDbContext`.
- BD PostgreSQL: mismas tablas `Customers`, `Applications`, `OutboxEvents`.
- `mock/` recibirá el **update** del evento (UC-13/14) — el mock actualiza, no duplica.

## Descripción

La solicitud fue aprobada y el SSN **ya existe** en la BD → el cliente regresa: se **actualiza** el Customer existente con los datos nuevos y la Application existente (p. ej. nuevo monto) — **sin crear duplicados** — y se agrega el evento de outbox con operación **update**, todo en una sola transacción.

## Contrato técnico (backend → frontend)

```
200 OK
{ "status": "approved", "applicationId": "<guid existente devuelto>", "reason": null }
```

Misma forma que UC-11 (el frontend no distingue create/update: ambos son "approved").

## Flujo principal (rama "regresa" del mismo caso de uso)

1. Normalizar el SSN a guiones `###-##-####` y buscar el Customer por ese SSN: **existe** → rama update.
2. `Customer.UpdateFromSubmission(SubmissionData)`: actualiza first/last name, address, city, state, zip, company (NO el SSN: es la clave, no cambia).
3. Actualizar la `Application` existente (p. ej. el `requestedAmount` nuevo).
4. Crear el evento de **outbox** con:
   - `Operation = Update`
   - `Payload` = customer + application (mismo shape; opcionalmente incluye el SSN para que el mock localice el registro).
   - `Status = Pending`
5. `SaveChanges()` → **una sola transacción**: `Update(Customer)` + `Update(Application)` + `Insert(OutboxEvent)` atomicamente.

## Transacción — qué pasa si falla

- Igual que UC-11: rollback total si algo falla. No queda customer actualizado a medias, ni application huérfana, ni evento publicado.
- El `IExceptionHandler` loguea (`Service=Niuro.Api`) y responde `500` Problem Details.

## Invariante de negocio

- **Mismo SSN = una sola fila en `Customers` y una sola en `Applications`**, siempre con la versión más reciente. La unicidad se garantiza en el modelo (índice único en `Customers.Ssn`) y en la lógica de la rama update del caso de uso.

## Postcondiciones

- Un solo Customer y una sola Application por SSN, con los datos más recientes.
- El evento `Update` (Pending) lo procesará el worker (UC-13) → el mock **actualiza**, no duplica.
